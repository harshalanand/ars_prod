# 2026-07-20

## Report Generation Hub — Reliability Hardening

Substantial session completing [[Report Generation Hub]] reliability work from 2026-07-20. Four major deliverables:

### 1. WhatsApp Configuration Module (DB-backed, Encrypted)
- Two dedicated tables: `APP_WHATSAPP_SETTINGS` (single active row) + `APP_WHATSAPP_AUDIT_LOG`
- Service: `app/services/whatsapp_settings_service.py` (get/save/test_connection/verify_template/send_test_message)
- API: `/settings/whatsapp` (RBAC: ADMIN_SETTINGS + SUPER_ADMIN for token modify)
- Token encrypted at rest via [[project_secret_encryption]] (Fernet, `APP_ENC_KEY` auto-generated in `.env`)
- Masks on UI, preserves on re-save
- Delivery integration: `report_delivery._provider_cfg('whatsapp')` reads decrypted DB config first
- Verified: 16/16 mocked service tests + live API + UI

### 2. Large-Data OOM Fix — Streaming Export
- Report 70 (USP_PARK_TEMP ~4.5M rows, USP_VAR_ART_ALC_RPT ~7M rows) was failing with "Unable to allocate 3+ GiB" MemoryError
- `data_export_service._export_one_resultset()` now peeks result-set size:
  - ≤250k rows → in-memory write (original path, fast)
  - >250k rows → streaming to CSV/xlsx via csv.writer (peak heap bounded 250k regardless of total)
- Peak memory: 48.5 MB vs old 3+ GiB
- Verified: 4/4 live DB tests (300k→3 files correct)

### 3. Split-Threshold Fix (Hierarchy + Row-Count Reconciliation)
- User-reported gap: 310k-row report (≤1M max_rows) was wrongly split into 4 SEG files
- Root cause: split threshold mixed 250k memory cap with "Max rows per file" setting
- **Fix:** split is NOW governed SOLELY by `max_rows` (user's setting), NOT memory cap
  - split OFF → single file (any size)
  - split ON & total ≤ max_rows → single file
  - split ON & total > max_rows → hierarchy (SEG/DIV/SUB_DIV/MAJ_CAT) or size chunks
- Adaptive two-pass local spill + LRU-bounded grouped writer for streamed data
- Verified: 12/12 unit + 4/4 live (300k→10 SEG×MAJ_CAT files correct)

### 4. Process Isolation (Separate OS Process)
- Fixed "app freezes during report generation" — ThreadPoolExecutor thread held GIL during CPU-bound pandas/CSV work
- New: `app/services/report_worker.py` — standalone entry `python -m app.services.report_worker <payload.json>`
- Scheduler launches via `subprocess.Popen` (detached: `CREATE_NEW_PROCESS_GROUP | CREATE_NO_WINDOW`)
- Controller thread just `proc.wait()`s (GIL-free)
- Health latency now ~0.22s consistently WHILE generating (was >25s frozen)
- Cancel: mark run 'cancelled' in DB + `proc.terminate()` the worker
- Verified: worker selftest + live run (pids 34572/37584)

### 5. Storage Guardrails (Retention Cleanup + Disk Pre-Flight)
- Root cause: output share \\File\...\98-ALC_REPORT filling up from old `FOLDER_PER_RUN` dated folders
- `cleanup_old_run_folders()` deletes `<base>/data/<YYYYMMDD>` folders older than `retention_days` (default 7)
- `assert_free_space()` fails a run early when free disk < `min_free_mb` (default 500)
- Config in `app_settings.json` 'reports' {retention_days:7, min_free_mb:500, cleanup_enabled:true}
- GOTCHA: retention is destructive by design (opt-in via cleanup_enabled:true) — auto-deletes old output
- Verified: 10/10 storage unit tests + live report run
